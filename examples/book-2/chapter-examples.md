# 第二本範例索引（配套素材，不是章節稿）

章節案例為可帶入專案工作的練習卡；本檔不代替書中概念說明或完整章節。既有可執行的大小寫搜尋缺陷在本資料夾 `search_tasks.py` 與 `test_search_tasks.py`。

| 章 | 情境／輸入 | Codex 任務起點 | 驗收條件 |
|---|---|---|---|
| 1 實戰工作法 | 需求：「待辦項目可標記完成」，但未說明重複操作或顯示方式。 | 「請列出必須釐清的問題，提出最小範圍與可測驗收條件；暫勿改檔。」 | 任務卡涵蓋輸入、狀態轉變、重複操作、錯誤情境及不在範圍內事項。 |
| 2 專案導覽 | 將待辦清單目錄交給 Codex；請它找入口、測試與資料流。 | 「先以檔案證據說明程式入口、資料讀寫位置和目前測試；每個結論列檔名，不修改。」 | 列出的路徑存在；不以猜測補齊沒有找到的架構。 |
| 3 小功能端到端 | 為待辦增加 `done <id>`，不存在的 id 不可改動資料。 | 「提出實作計畫和邊界測試，確認後修改；測試有效 id、未知 id、重複完成。」 | 測試覆蓋成功、未知及重複操作；diff 不混入無關重構。 |
| 4 追查錯誤 | `search_tasks.py` 的搜尋區分大小寫，測試要求不區分；先執行 `python3 -m unittest -v test_search_tasks.py`。 | 「先重現並解釋失敗；不得先改測試來遷就程式。提出最小修正，保留顯示文字原樣。」 | 原始版本出現預期斷言失敗而非匯入錯誤；修正後所有測試通過。 |
| 5 重構 | 重構搜尋函式時保持現有輸入輸出與空查詢行為。 | 「先列出重構前行為與測試保護；小步重構，不新增功能。」 | 原測試全部通過；重構前後外部行為一致，差異集中於目標程式。 |
| 6 測試設計 | 搜尋資料：`Review API design`、`Test api client`；查詢 `api`、`API`、空字串。 | 「整理測試矩陣，分清正常、邊界與無效輸入；先指出每列預期結果。」 | 大小寫兩種查詢結果一致；空字串無結果；文字顯示保留原始大小寫。 |
| 7 需求變更 | 原需求只搜尋，追加「結果需依原始順序」。 | 「指出新增要求會影響的程式與測試；保留既有順序及大小寫行為。」 | 測試含非字母排序反例；新增要求與既有需求皆通過。 |
| 8 Review 與修正 | 請 Codex 審查同一個搜尋 diff，要求每項發現標示嚴重度、位置、重現方式。 | 「不要直接改碼；提供可驗證問題，並區分確定缺陷與建議。」 | 人工逐項對照程式與測試；假警報不照單全收，已確認缺陷補回歸測試。 |
| 9 非互動執行 | 將一次性低風險任務描述成可透過 Codex 官方 `exec` 支援的批次工作；先查當版 help/reference。 | 「不得假設旗標；先列出需確認的執行模式、模型、工作目錄、權限與輸出格式。」 | 只使用已核實的當期 CLI 命令；失敗狀態可見，不把空輸出當成功。 |
| 10 綜合演習 | 對待辦清單交付一項功能、一道 bug 修正及回歸測試。 | 「先分解為有序任務，每步列驗收；完成每步後檢查 diff 和測試再往下。」 | 交付包含重現證據、功能驗收、測試結果、diff review 與尚未完成事項。 |

可接受輸出會因程式設計而異；上述條件以可觀察行為為準，不要求模型逐字回答範例。
